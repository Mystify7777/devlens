# 0009: What should define v0.3.0-alpha?

## Status

Accepted — Option A (Interactive Inspection)

## Context

As of this ADR, the project stands at:

- Core ✅ complete, tested
- Runtime ✅ complete, tested
- Console ✅ complete, tested
- Panel ✅ complete, tested
- Playground ✅ working, exercises the full pipeline manually
- 108 test cases across the suite
- README merged, documenting architecture and status
- End-to-end pipeline proven: Runtime/Console → EventBus → EventStore →
  Panel, with a real event visibly rendered in a live overlay

ADR-0008 already flagged this fork explicitly, in its own "Explicitly
deferred" section:

> Search, filtering, inspector — likely ADR-0008 amendment or a new
> ADR-0009 once v1 rendering is proven.

v1 rendering is now proven. This ADR is that follow-up.

The original roadmap ordering (Core→Runtime→Console→Playground→Panel→
Network→React) was set before the Panel existed, when "get something on
screen" was the only real bottleneck. Now that a Panel exists — even a
deliberately minimal one — the next milestone is a genuine fork rather
than a forced next step. This ADR exists so that fork is decided
explicitly, the same way Panel's scope was decided before any of its
files were written, rather than being settled implicitly by whichever
package happens to get coded first.

The question is framed at the product level — the central question of
this ADR is:

> **What should v0.3.0-alpha be about?**

— rather than as a binary "Inspector vs. Network" package choice,
because the two options below aren't mutually exclusive forever.
They're a choice about sequencing and theme, not about permanently
excluding one.

This ADR intentionally does not evaluate implementation effort,
estimated timeline, or contributor availability. Those influence
planning, but they are not architectural arguments. The purpose of
this ADR is to choose the theme and scope of the next milestone based
on the long-term direction of the project, not on which option looks
faster to build today.

## Option A: Interactive Inspection

**Goal:** make the events DevLens already captures significantly more
useful, without adding a new capture source.

Possible scope:
- Inspector drawer/detail view (stack traces, `metadata`, `context`, `tags`)
- Filtering by category and severity
- Search
- Pause/resume capture
- Clear events
- Export/import event sessions (JSON)

**Pros**
- Builds directly on architecture that already exists and is tested —
  no new Plugin, no new normalizer, no new listener surface.
- Every future capture source (Network, and anything else added later)
  inherits these capabilities for free, rather than each new plugin's
  events being viewed through the same minimal list.
- Turns DevLens from "a live event feed" into something closer to an
  actual debugging tool.

**Cons**
- Doesn't increase capture coverage — someone cloning the repo today
  still can't see network activity in DevLens after this milestone.
- Some of this scope (inspector, filtering) will interact with Panel's
  existing constraints (e.g. `MAX_RENDERED_EVENTS`, the "renderer takes
  the whole ShadowRoot" deferral noted in ADR-0008) sooner than
  Network would, meaning this option is more likely to force revisiting
  settled Panel decisions.

## Option B: Network Capture

**Goal:** capture a second major class of browser events, following
the same Plugin contract as Runtime and Console.

Possible scope:
- `fetch` interception
- `XMLHttpRequest` interception
- Request lifecycle (start/end/timing)
- Response metadata (status, headers, size)
- Failed request detection

**Pros**
- Widens what DevLens can see — arguably the more immediately
  compelling capability to a new user ("it also catches failed API
  calls") compared to inspection tooling on data it already has.
- Follows the same Plugin/normalizer pattern already proven twice
  (Runtime, Console), so the implementation risk is well understood.

**Cons**
- The Panel remains a simple, unstyled list. Network events tend to
  carry more structured data (headers, timing, payloads) than a
  console log or a stack trace — data that's harder to usefully
  represent in the current minimal row (severity/title/message only)
  without at least some of the inspection work from Option A.
- Doesn't change the experience of anything already captured.

## Decision criteria

Rather than "which package do we want to build," the more useful
question is:

> Which milestone makes DevLens meaningfully more useful to someone
> cloning the repo today?

Secondary considerations worth weighing alongside that:
- Does the option risk reopening ADR-0008 decisions that were meant to
  stay settled (e.g. the ShadowRoot/renderer container split)?
- Does the option compound — do future plugins/milestones inherit its
  benefit for free, or is its value contained to itself?
- Which option keeps v0.3.0-alpha a single coherent theme, the way
  Panel gave v0.2.0-alpha its identity, rather than a grab-bag of
  unrelated additions?

## Decision

**v0.3.0-alpha: Interactive Inspection.** Option A is selected.

The deciding argument was the compounding effect Option A has that
Option B doesn't:

```text
Investing in inspection first:

  Runtime  ┐
  Console  ├──►  richer UI
  Network  ┘     (every source benefits)

Investing in Network first:

  Runtime  ┐
  Console  ├──►  same UI
  Network  ┘     (breadth increases, experience doesn't)
```

Network capture remains valuable and is not rejected — it's deferred,
the same way Panel's search/filtering/inspector were deferred rather
than rejected in ADR-0008. This decision is about sequencing and theme,
not about permanently excluding Option B.

This also surfaced a useful mental model for future roadmap decisions:
DevLens now has two distinct axes of growth, and each milestone should
pick one deliberately rather than mixing both:

```text
Capture axis          Experience axis
-----------          ----------------
Runtime               Panel
Console               Inspector
Network                Filtering
React                  Search / Timeline / Export
```

v0.1.x-alpha proved the event pipeline. v0.2.0-alpha built the Panel.
v0.3.0-alpha invests in the Experience axis: making already-captured
events understandable, not capturing more of them.

## Consequences

In scope for v0.3.0-alpha (exact package/file breakdown to be settled
in its own ADR, following the same process as Panel — ADR first,
review, then implementation):

- Inspector drawer/detail view (stack traces, `metadata`, `context`, `tags`)
- Filtering by category and severity
- Search
- Pause/resume capture
- Clear events
- Export/import event sessions (JSON)

Explicitly deferred, not rejected:

- Network capture (`@devlens/network`) — remains the natural Capture-axis
  follow-up once Experience-axis work lands.
- React wrapper (`@devlens/react`) — depends on Panel's public surface,
  which this milestone may still change.

Flagged as likely to require revisiting settled Panel decisions from
ADR-0008, rather than being purely additive:

- The renderer currently owns the entire `ShadowRoot` (ADR-0008,
  "Rendering strategy"). An inspector drawer and filter/search controls
  imply real Panel structure (header/toolbar/list/footer) — this is the
  concrete trigger, flagged back in the Panel test-review discussion,
  for finally narrowing the renderer's container to a dedicated
  `eventListContainer` sub-element instead of the whole `ShadowRoot`.
  This should be handled as its own amendment to ADR-0008 rather than
  silently changed mid-implementation.
- `MAX_RENDERED_EVENTS` and its slicing policy in `panel.ts` may need
  reconsideration once filtering/search exist — filtering a 300-event
  window is a different feature than filtering the full Store.
